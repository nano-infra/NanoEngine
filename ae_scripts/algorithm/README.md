# Reproducing the Dynamic SP Bucket Search

This directory measures and searches the sequence-length-to-SP-size policy
used by NanoDeploy for MLA decode. It includes the supplied DeepSeek-V3 grid
and a KIMI K2 measurement pipeline. Run all commands from the `ae_scripts`
directory.

## Resource and time estimate

| Stage | GPUs | Expected time |
| --- | ---: | ---: |
| Optional latency remeasurement | 8 H200 GPUs | about 20–40 minutes |

The normal reproduction uses the supplied CSV. The GPU stage is optional.

## Files

| Path | Description |
| --- | --- |
| `algorithm/deepseek_v3_h200_pipeline_p50.csv` | P50 decode-pipeline latency for every measured sequence length and SP size |
| `algorithm/measure_sp_pipeline.py` | Optional single-node GPU measurement launcher |
| `algorithm/measure_sp_pipeline_kimi.py` | KIMI K2 single-node GPU measurement launcher |
| `algorithm/test_sp_attention_cudagraph.py` | Local SP attention CUDA Graph benchmark entry point |
| `algorithm/search_sp_buckets.py` | Monotonic bucket-search implementation |
| `algorithm/reproduced_policy.json` | Policy and regret summary generated by the search |

The input CSV contains 2,064 measured settings: 258 sequence lengths and SP
sizes 1 through 8. Each setting records its sample count and was collected on
NVIDIA H200.

## Reproduce the policy

```bash
python3 algorithm/search_sp_buckets.py
```

The command validates the measurement grid and overwrites
`algorithm/reproduced_policy.json` with the reproduced bucket policy and prints
the resulting sequence-length intervals.

To select different input and output files, use `--input <measurement-csv>` and
`--output <policy-json>`.

## Optional: remeasure the latency grid

This step runs the NanoDeploy single-request MLA CUDA Graph benchmark on one
node. It measures all 258 sequence lengths with SP sizes 1 through 8, aggregates
the master-rank latency into a fresh P50 CSV, and searches a policy from that
CSV. It uses the `hao_basic` SP communication backend. Fresh latency values and
bucket boundaries may differ slightly because of GPU measurement noise.

Run on a node with eight visible H200 GPUs:

```bash
CUDA_VISIBLE_DEVICES=0,1,2,3,4,5,6,7 \
python3 algorithm/measure_sp_pipeline.py \
  --samples 3 \
  --warmup 20 \
  --iterations 100 \
  --output-dir algorithm/results/ae_fast
```

The DeepSeek launcher retains its existing NanoDeploy checkout discovery. The
KIMI K2 launcher below uses the local `algorithm/test_sp_attention_cudagraph.py`
entry point and does not require a checkout parameter.

The command collects three samples per setting and reports their median. Each
sample uses 20 warmup and 100 measured CUDA Graph replays. The benchmark also
performs ten internal warmup replays before graph capture. The run writes:

```text
algorithm/results/ae_fast/
├── config.json
├── logs/sp*.log
├── raw/sp*.csv
├── deepseek_v3_h200_pipeline_p50.csv
└── reproduced_policy.json
```

If the run is interrupted, resume completed samples with:

```bash
CUDA_VISIBLE_DEVICES=0,1,2,3,4,5,6,7 \
python3 algorithm/measure_sp_pipeline.py \
  --samples 3 \
  --warmup 20 \
  --iterations 100 \
  --output-dir algorithm/results/ae_fast \
  --resume
```

Add `--dry-run` to inspect the complete planned workload without launching GPU
processes.

## Measure and search KIMI K2

`measure_sp_pipeline_kimi.py` measures the same single-request MLA decode
pipeline with the KIMI K2 attention dimensions:

| Parameter | Value |
| --- | ---: |
| Query heads | 64 |
| Q/K head dimension | 576 |
| FlashMLA output head dimension | 512 |
| MLA KV heads | 1 |
| SP sizes | 1 through 8 |

The FlashMLA output head dimension is 512 because it is the latent attention
output communicated by the kernel. KIMI K2's model-level `v_head_dim=128` is
applied by the later value projection and is not the value for this benchmark.
The default sequence grid covers 1024, 2048, every 4096 tokens, and the
1,000,000-token endpoint.

The measurement and search stages can be run separately. Use a fresh output
directory for each measurement run:

```bash
CUDA_VISIBLE_DEVICES=0,1,2,3,4,5,6,7 \
python3 algorithm/measure_sp_pipeline_kimi.py \
  --samples 3 \
  --warmup 20 \
  --iterations 100 \
  --output-dir algorithm/results/kimi_k2
```

The measurement launcher automatically runs the search when all SP sizes and
at least three sequence lengths are measured. It writes:

```text
algorithm/results/kimi_k2/
|-- config.json
|-- logs/sp*.log
|-- raw/sp*.csv
|-- kimi_k2_h200_pipeline_p50.csv
`-- kimi_k2_policy.json
```

To rerun the search explicitly from the measured CSV:

```bash
python3 algorithm/search_sp_buckets.py \
  --input algorithm/results/kimi_k2/kimi_k2_h200_pipeline_p50.csv \
  --output algorithm/results/kimi_k2/kimi_k2_policy.json
```

The search requires every sequence length to contain measurements for SP sizes
1 through 8. If the GPU run is interrupted, resume it with the same arguments
and `--resume`:

```bash
CUDA_VISIBLE_DEVICES=0,1,2,3,4,5,6,7 \
python3 algorithm/measure_sp_pipeline_kimi.py \
  --samples 3 \
  --warmup 20 \
  --iterations 100 \
  --output-dir algorithm/results/kimi_k2 \
  --resume
```

Every KIMI K2 measurement must use `hao_basic`. If an interrupted output
directory contains `backend=legacy_ll` in its logs, do not resume it; choose a
fresh output directory and rerun the measurement.

Use `--seq-len` to measure a smaller explicit grid, or `--dry-run` to inspect
the worker commands without launching GPU processes. A subset grid is useful
for smoke testing but cannot produce a complete bucket policy until all SP
sizes and at least three sequence lengths are present.
