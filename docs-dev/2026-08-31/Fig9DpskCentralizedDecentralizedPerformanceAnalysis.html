一句话结论

结果支持“去中心化能显著压低大规模 scheduler critical path”。在 32 logical nodes 模型中，admission 和 decode mean 对所有五个 Fig9 点都取得明确优势；decode 的 4→32 扩展倍率从中心化的 9.83× 降到去中心化 critical path 的 1.82×。
结果不支持“去中心化端到端一定更快”或“去中心化总 CPU 更少”。32-node 是单机上的独立 LocalScheduler replica 模型；Router、transport、receipt、barrier、Ray/RDMA 和 GPU 均不在主指标中。去中心化 aggregate CPU 更高，完整控制面诊断也明显高于主 critical path。

不能直接主张的结论

  • 不能把 32-node 模型写成真实 256-GPU 分布式 wall-clock。

逐点对比

加速比 = 中心化 mean / 去中心化 critical-path mean；大于 1 表示去中心化更快。Pending SP8 是从固定 seed=0 的 workload 生成器重算出的本轮新入队长请求数。

4-node：Admission 结论不稳定

去中心化只在 2/5 点胜出；几何平均加速 1.11×，但中位加速仅 0.95×。这不足以形成“4-node admission 普遍更快”的结论。

主要混杂因素是新 cohort 的 SP8 构成。issue5_r50 的 80 个新请求中没有 SP8 请求，因此中心化 admission 只有 0.946 ms；r40/r45 分别含 5/7 个新 SP8 请求，中心化耗时跃升到 40.736/24.408 ms。跨点非单调主要反映 workload composition，而非 rate 单变量响应。

同一 case 内中心化和去中心化使用相同请求集合，因此逐 case A/B 仍有效；不同 Fig9 点之间不应直接做趋势拟合。

32-node：Critical path 一致改善

五个点全部胜出，去中心化 mean 为 13.588–27.299 ms，中心化为 74.046–144.805 ms；逐点加速 4.67–8.80×，几何平均 5.87×。

这是一条明确的算法扩展性信号：把 admission commit 分到 32 个独立 LocalScheduler 后，最慢 local commit 仍显著小于单个全局 Scheduler 的调度时间。

但这不是完整控制面延迟：Router load/plan、receipt、transport 和 local commit 的真实并发没有进入主值。

Admission 的“关键路径”与“总工作”

32-node aggregate local commit CPU 是中心化的 1.47–1.61×（几何平均 1.51×）。完整控制面诊断为中心化主值的 1.92–4.57×，但其中 local commit 是串行求和，不能当成真实并行 wall-clock。部署收益依赖真正并行提交以及 Router/receipt 路径优化或 overlap。

Critical path 与 aggregate work 分离

去中心化 critical每个 quantum 取最慢 LocalScheduler：max(local)。这是主延迟指标。
去中心化 aggregate把所有 LocalScheduler CPU 相加：sum(local)。这是容量成本，不是延迟。
观察32-node decode critical 只扩 1.82×，aggregate 却扩 9.48×；延迟收益来自并行化，不来自减少总 scheduler work。

容量成本

相对单个中心化 Scheduler，去中心化 aggregate decode CPU：

  • 4-node：高 17.1–30.1%，几何平均高 25.2%。
  • 32-node：高 15.4–29.9%，几何平均高 20.8%。
这是一项可接受性取决于部署目标的 trade-off：用更多并行 CPU 容量换取更短 critical path，并消除全局 Scheduler 随规模增长的串行瓶颈。

建议的下一步验证

  1. 对 4-node admission 使用多个 seed 重跑，按“pending SP8 数/每 local 分布”分层报告，而不是只按 rate 排序。
  2. 在真实 4 节点部署中记录统一 barrier 下的 Router start/end、每个 LocalScheduler start/end、receipt 与 coordination wait。
  3. 将 scheduler critical、aggregate CPU、完整控制面 wall-clock 和端到端 TPOT 四个口径并列，确认并行收益没有被 transport/coordination 吞掉。
  4. 对 decode 尖峰追加至少 5 次独立重复或更多样本，报告 run-level P95/P99 区间，定位 local straggler 来源。
