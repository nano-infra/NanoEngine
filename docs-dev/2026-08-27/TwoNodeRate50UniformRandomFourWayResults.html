Two-node rate-50 four-way scheduling comparison

Two repetitions compare centralized and hierarchical scheduling with LeastBatch and ProjectedLoad on an identical 15,000-request trace.

Hierarchical + ProjectedLoad is the clear winner. The architecture contributes roughly 7% lower TPOT; ProjectedLoad adds roughly 2% by reducing attention-work skew. The architecture win is host/control-path savings—not faster GPU execution or a cheaper schedule() call.

How the global critical path was reconstructed

Central diagnostics contain one global record per quantum. Hierarchical diagnostics contain one record per engine, so records are grouped by (wave_id, quantum_id) and the engine with the maximum quantum_total_ms is selected as the global critical record. Where the win is—and is not

Not faster GPU/model execution Cumulative executor time is 1.2–1.5% higher under hierarchical scheduling. GPU rank time per output token is also slightly higher.
Not a cheaper schedule() call LeastBatch scheduling rises from 0.705 s to 0.881 s accumulated, about 1.61 ms versus 1.98 ms per global critical quantum.
Yes: host critical-path savings Roughly 13 s of in-quantum residual and 6 s outside decode quantums leave the serialized centralized path.

Central synchronous add acceptance averages 0.40–0.44 ms/request. Across 15,000 requests, that is 6–6.6 seconds and is consistent with most of the centralized time outside recorded decode quantums. Under Poisson bursts it also accumulates into visible dispatch lag.

The supported interpretation is therefore broad: hierarchical scheduling removes centralized host orchestration and ingress serialization from the critical path. It does not make the scheduler algorithm itself cheaper.

Corrected TPOT contract

Corrected tpot_with_queue_ms uses a scheduler execution boundary for both architectures, keeps GPU-capacity queue time, and removes unused decode slots from the final fixed 16-loop quantum. It excludes benchmark dispatch, non-capacity RPC/command pickup, and non-capacity waiting before first scheduler execution.

This is why the TPOT result is useful for steady-state scheduling, but Arrival E2E remains necessary for user-visible end-to-end behavior.

Tail diagnostic retained

Hierarchical ProjectedLoad repetition two contains a rare control-path outlier: global-capacity-queue max is 300.528 ms and admission-RPC max is 323.793 ms. Capacity-queue p99 remains zero and admission-RPC p99 is 5.478 ms, with no failure or retry. It does not change the aggregate conclusion but should remain visible in future tail comparisons.

What is confirmed

In this instrumented rate-50 comparison, the hierarchical stack lowers latency primarily by removing centralized host-side orchestration and synchronous ingress serialization from the critical path. It does not win through lower GPU execution time or a faster measured schedule(). ProjectedLoad adds a separate load-balance gain.

This uses “scheduling overhead” in the broad system sense of centralized control-path serialization. It must not be shortened to “the scheduling algorithm became cheaper.”

What is not yet confirmed

  • The roughly 13-second central quantum residual is not subdivided. It contains metrics updates, output construction, rank-load diagnostic payload construction, per-step logging, and Python bookkeeping between measured stage boundaries.
  • Quantum diagnostics are enabled everywhere, but their implementation cost may be asymmetric. The result localizes the gain to the host path; it does not fully separate production orchestration from diagnostic overhead.
  • Central uses Ray worker transport and hierarchical uses ZMQ. The experiment compares current deployable stacks, not an isolated scheduler-architecture coefficient.
  • Every repetition uses the same C-LB, H-LB, C-PL, H-PL order, so time/order drift is not counterbalanced.
  • Two system repetitions establish a consistent direction, not a precise effect-size confidence interval or capacity knee.

Recommended confirmation runs

  1. Repeat the four-way comparison with quantum diagnostics disabled.
  2. Add timers around central pre-executor bookkeeping, postprocess-to-return work, diagnostic construction, logging, and frontend add.
  3. Isolate worker transport where the runtime supports it.
  4. Counterbalance configurations with ABBA or Latin-square ordering over at least four repetitions.
  5. Sweep above rate 50 to locate each stack's goodput/capacity knee.

For the current production choice at rate 50, evidence favors hierarchical + least_projected_load. These follow-ups are for causal attribution and capacity characterization, not because the observed whole-stack ordering is ambiguous.
