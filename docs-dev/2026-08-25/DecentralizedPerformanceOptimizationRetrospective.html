去中心化性能优化复盘

我们没有通过删除同步或削弱 admission 正确性来换性能，而是把重 CPU 数据处理移出关键边界，并把“可靠接管”与“权威提交”拆成可流水化的两阶段协议。结果是 quantum-long stop-and-wait 被解除；剩余约 3.3% 的 corrected TPOT 差距，已经主要指向执行量子而不是请求分发。

范围：2026-08-24—25 拓扑：2 机 · DP2/SP8/EP16 负载：rate 40 · 12,000 requests 代码证据基线：e1245f2 核心改动：07cc0f2 → 0105380 → 1c7b147 → baf3fbc

一句话结论

本轮最有效的优化不是某个 kernel 或一次更快的 RPC，而是一次协议级去串行化：将原先“Router 发批次 → 等 LocalScheduler 跨过下一个 quantum 边界并 commit → 收 ACK → 才能发下一批”的事务，改为“LocalEngine 有界接管 → 毫秒级 receipt → Router 继续发 → event-loop 在安全边界 commit → AddResult 最终确认”。

已经解决：单个 admission flight 不再占住约一个量子的时间，也不再把同 engine 的后续请求锁在 Router；完整 Sequence 仍只传一次，精确 SP/KV reservation 仍持续计费，scheduler 仍由 event-loop 单写。
尚未解决：单个请求仍可能等待下一个 loop-count-16 安全边界。这个等待从同步 RPC 中被显式拆成 staged_queue_ms，并未凭空消失；若要继续优化 TTFT，需要改变 safe-boundary 粒度或执行量子，而不是继续压缩 3 ms 的 receipt。

性能优化的真实成功点

消除了 Router flight 与 scheduler commit 的错误耦合，使请求分发具备吞吐流水线。旧版约 1,018.5 ms 的 Local command queue 不再藏在 RPC ACK 内；Router/global capacity queue 从 506.719 ms 降到 0.018 ms。

!

不能得出的结论

不能说新版端到端已经优于中心化。当前同拓扑 A/B 中，去中心化 corrected TPOT 为 67.561 ms/token，中心化为 65.404 ms/token；其差距的约 96% 来自 corrected 执行边界，而不是新增的 pre-GPU 控制边界差。

本轮优化可以概括成四层

算法层

删除伪 capacity probe

不再在安全边界创建 prompt-sized 零 Sequence 来探测容量。

数据层

Opaque Sequence 一次传递

sidecar 用于路由，完整 C++ Sequence 作为不透明 payload 保留所有权语义。

传输层

持久 ZMQ 批量通道

一个 metadata frame + N 个 payload frame，避免 Ray payload RPC 与 Python token 展开。

协议层

Receipt / commit 两阶段

快速可靠接管与权威 scheduler 提交解耦，同时保留 boundedness 和精确 charge。

诊断上的最大转折：从“同步太多”转为“工作放错了边界”

最初容易把差距归因于 Gloo/EP 全局同步或去中心化架构本身。代码路径和 CPU profiling 纠正了这个判断：全局同步是当前执行语义所需，steady-state scheduler 本身也很轻；真正危险的是 LocalEngine 单写 event-loop 在 quantum 顶部串行执行与 prompt 长度成正比的数据转换和 admission 工作。

被证伪或降级的假设

  • “Gloo/EP 同步就是主因”：旧 paired A/B 的 worker critical quantum 仅 811.626 vs 812.184 ms，差 0.069%。
  • “Python load snapshot / planner 很慢”：代表性测量约 0.15/0.26 ms，不能解释约 1 秒延迟。
  • “网络按请求逐个 RPC”：原实现已按 engine 聚合，约 19.9 requests/message；问题是每 engine 仅允许一个长生命周期 flight。
  • “把 token ids 删除就够了”：会破坏后续 P/D、迁移与恢复所需的完整 Sequence 所有权，不是可接受的生产优化。

最终被证据支持的因果链

  1. frontend 把完整请求发给 LocalEngine。
  2. 同步 handler 等待 event-loop 的 scheduler commit 才回 ACK。
  3. event-loop 每个 quantum 顶部只 drain 一次 command；错过后要等约 812 ms。
  4. Router 在 ACK 未完成时禁止向该 engine 发下一批。
  5. 于是单请求的相位等待升级为同 engine 后续请求的队头阻塞和约一秒的 flight。

为什么旧指标一开始没有直接暴露问题

历史 quantum 计时在 command drain 之后才记录 quantum_begin，因此 admission 在“上一量子结束 → 下一量子计时开始”之间的缝隙中执行，既不进入 execute latency，也不进入 scheduler latency。复盘中新增并拆分了 scheduled arrival、actual dispatch、receipt、commit、first forward 和 terminal 六个边界。

T0 scheduled arrival └─ dispatch_lag ─► T1 actual dispatch └─ router / transport ─► T2 positive receipt (bounded ownership) └─ staged_queue ─► T3 AddResult (authoritative commit) └─ local_scheduler_queue ─► T4 first forward └─ real-token execution ─► T5 terminal
方法论：只要计时边界没有覆盖线程切换、事件循环 drain 或批次闸门，最重的等待就可能落在“不可见区”。先补全事件时间线，再讨论优化对象。

不是“少传字段”，而是重新定义数据所有权

路由只需要 prompt length、max tokens、request id 和 placement reservation 等 sidecar；执行和未来 P/D 则需要完整 Sequence。最佳边界是：控制面读取小型 sidecar，数据面搬运 opaque payload，中间组件不展开自己不理解的对象。

sidecar: request_id / lengths / reservation payload: opaque C++ Sequence bytes serialize once → send once → deserialize once

不是“取消 ACK”，而是缩短 ACK 的语义

应用层 receipt 仍必须存在，否则发送方无法确定远端是否取得 payload 所有权。变化在于 receipt 只承诺“bounded staged ingress 已建立”，不再承诺“scheduler 已 commit”。未知 receipt 采用 fail-stop，防止重传导致双重所有权。

receipt = ownership + bounded slot AddResult = authoritative scheduler commit snapshot = watermark reconciliation

双水位保证不会重复计费

  • ingress_version：positive receipt 的单调所有权水位。
  • admission_version：scheduler commit 的权威水位。
  • snapshot 未覆盖的 receipt 继续补计 staged slot。
  • SP/KV reservation 持续到 admission watermark 或 terminal，receipt 不能提前释放。

正确性不变量

  • LocalScheduler 仅 event-loop 单写，ZMQ thread 不直接修改。
  • positive receipt 后 payload 禁止重传，transient mismatch 本地 FIFO 重试。
  • staged + committed lifecycle slots 有界。
  • FIFO head 暂时不 fit 时，不越过依赖其 shadow 的后续 reservation。
  • receipt outcome 未知时 fail-stop，不冒险 requeue。

反向控制面也从 barrier 改为 progress engine

原 frontend cycle 通过 ray.get([engine_0, engine_1, ...]) 同步等待所有 engine 的事件和 load，可能让一个慢 actor 阻塞另一个 engine 的 ZMQ progress。新版为每个 engine 保留一个 outstanding event ref，ray.wait(timeout=0) 只消费 ready ref、立即 re-arm，并为每个 flight 保留 deadline watchdog。

poll ready per-engine events (timeout = 0) ├─ consume ready load / AddResult / lifecycle events ├─ re-arm only the completed engine └─ fail an overdue flight by deadline poll ingress receipts → reconcile watermarks → plan → flush

为什么 raw dispatch 看起来差得更多

中心化：scheduled arrival ── 515.894 ms ──► dispatch ─► execute ↑ raw dispatch TPOT 从这里才开始 去中心化：scheduled arrival ── 0.120 ms ──► dispatch ── staged ─► execute

所以公平的用户到达视角应看 scheduled-arrival TPOT；执行效率视角应看 corrected TPOT。两者回答不同问题，不能只挑更好看的一个。

可泛化的优化框架

优先级 ≈ 串行关键路径时长 × 发生频率 × 阻塞扇出
不是“函数自身耗时最大”，而是“它让多少后续工作无法推进”

这套方法适用于分布式调度器、actor 系统、存储 ingestion、消息队列和控制/数据面混合服务。它强调协议依赖、所有权和计时边界，而不是只优化局部函数。

1

先定义六个端到端边界

至少区分 scheduled arrival、actual dispatch、receipt、authoritative commit、first execution 和 terminal。任何两个边界之间都应能独立统计 mean/p99/max；否则 backlog 很容易从一个阶段“搬”到另一个阶段并被误判为消失。

2

画等待依赖图，寻找长 flight 和 phase lock

查看“谁在等谁、等待期间谁不能继续发”。本例真正的放大器不是 4 ms admission，而是 ACK 等待 commit 时 Router 禁止下一批，导致一个请求的相位等待阻塞约 20 个请求的后续 flight。

3

按执行位置分类，而不只按总 CPU 时间分类

把工作分为 safe-boundary 串行、可与 accelerator overlap、frontend 异步和 offline 四类。即使总工作不变，只要把 O(payload) 的 decode/validation 移出 quantum boundary，也能显著缩短临界路径。

4

把“接收”与“生效”拆成两阶段

当下游只能在离散安全点修改状态时，不要让上游同步等待生效。先做有界、可确认的 ownership transfer，再由单写者在安全点 commit；最终结果走异步事件。数据库 WAL、存储 ingest 和异步编译也适用这一模式。

5

用 credit / watermark 保住背压

流水化不能等同于无限排队。发送方在 receipt 后继续保留资源 charge；接收方原子预留 bounded slot；snapshot 用单调水位告诉发送方哪些 receipt 已被远端状态覆盖，避免 double count 和提前放贷。

6

控制面看 sidecar，数据面传 opaque object

如果路由组件只需要少量元数据，就不要让它展开完整对象。把可解释的调度字段放 sidecar，把复杂状态保留为 opaque payload；这样既减少转换，也保持未来扩展的所有权和兼容性。

7

用 progress engine 替代 all-shard barrier

每个 shard 保持独立 outstanding flight，只消费 ready completion，并为每个 flight 设置 deadline。一个慢节点不应阻塞其他节点的 ingress、load 更新或事件消费。

8

建立 CPU → 跨节点 CPU → GPU 的验证阶梯

CPU 可以直接验证协议吞吐、batching、序列化、ownership、boundedness、重试和 actor placement；GPU 只用于验证 quantum overlap、RDMA、执行效率和端到端指标。这样既节省资源，也让故障归因更清楚。

正确的性能问题问法

  • 这段工作是否位于串行 critical path？
  • 它的完成是否阻止下一个 batch 或其他 shard？
  • 时间是固定成本，还是 O(requests)、O(tokens)、O(ranks)？
  • 并行 shard 应取 max、sum 还是带 barrier 的 max + skew？
  • 优化后等待真的消失了，还是换了计时边界？

当前不足：控制面主瓶颈已换挡，执行差距仍在

这轮改动达成了“解除 admission stop-and-wait”的主要目标，但没有达到原设计文档中“corrected TPOT mean 回归不超过 1%”的验收线。当前 paired A/B 为 +3.298%，worker/executor quantum 约 +1.17%；下一轮应该围绕执行相位与量子打包做对称 profiling。

优先级 P0：解释 corrected TPOT 的 3.3%

  1. 在中心化和去中心化两边同时开启相同 quantum diagnostics，比较 useful real batch、dummy slots、send_seqs、worker critical 和 result tail。
  2. 对同一 token trace 做交错运行（H/C/H/C），避免单次顺序运行的温度、节点和后台负载偏差。
  3. 核对 admission phase 改变后，两 engine 的 batch packing、首批进入时机和 active sequence 分布是否偏移。

优先级 P1：如果目标包含 TTFT，再缩短 staged wait

  1. A/B loop count 16 vs 8，衡量 staged p50/p99、worker critical、协调频率和吞吐。
  2. 评估是否存在 executor 内部更细但仍安全的 admission 边界；不得让 ZMQ thread 直接写 scheduler。
  3. 对短输出请求单独观察 normalized boundary；当前 staged wait 占控制边界约 92.2%，短输出对固定等待更敏感。
