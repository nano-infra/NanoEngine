Hierarchical Async Scheduling · 下一步实验计划

目标不是只证明 depth=2 能运行，而是分别回答三件事：token / EOS / abort 是否完全正确；哪些 CPU 工作确实落在上一 quantum 的 GPU 窗口内；最终 exposed latency 与吞吐是否改善。

代码基线 a88ec6a CPU + control-plane + ZMQ 回归已过 GPU 实测待执行 2026-08-25 观测：8×H200 仅余约 13.7–14.2 GiB/卡
H1

正确性不变

depth1 与 depth2 在固定 seed 下逐请求 token IDs、offset、长度、finish reason 完全一致。

H2

CPU/launch 被覆盖

q GPU 执行期间完成 q+1 schedule、serialize/send、worker recv/prepare、metadata H2D 与 graph replay launch。

H3

D2H 不再卡住 q+1

q sampled token 通过 GPU carry 喂给 q+1；q 的 D2H 与 .tolist() 延迟到 FIFO collect。

关键判据是区间相交，而不是仅看到调用顺序。depth=2 的 CPU 单测已经证明 submit/collect 顺序；GPU trace 仍需证明 host q+1 工作确实发生在 q CUDA kernel 尚未结束时。

已具备

  • 两 flight FIFO、两 payload slot、严格按序 commit。
  • request ID + generation epoch 的 GPU token carry。
  • 独立 copy stream、pinned host buffer、deferred .tolist()。
  • EOS/abort semantic finish 与 resource release fence 分离。
  • quantum diagnostics 中已有 schedule、transport、worker、GPU loop、D2H 指标。

最终 timeline 前仍需补的轻量观测

  • 给 quantum diagnostic 增加 plan/submit/collect 与 worker prepare/launch/D2H 的 monotonic begin/end。
  • 记录 flight queue depth、stale EOS/abort forward、deferred KV block hold time。
  • 让 correctness harness 输出逐 request token manifest。
  • bench 暴露 profiler_mode=runtime_overhead，否则默认 profiler 只有 CUDA lane，无法证明 CPU overlap。

指标读取顺序

协议正确→token manifest→资源 fence→timeline overlap→吞吐 / ITL

前一层失败时不解释后一层性能。尤其不能在 token 不一致或 stale commit 存在时，用更高吞吐宣称成功。

Correctness hard gates

  • depth1/depth2 manifest：request ID、每个 token ID、offset、finish reason 全相同。
  • 每个 quantum 的 wave/quantum/slot/epoch 校验均通过。
  • EOS/abort 后无 token commit；release 只发生在最后 referencing flight drain 后。
  • 所有 owner、reservation、KV block、worker pending output 在结束时归零。

Pipeline hard gates

  • 稳定连续 request 在 q0 后出现 gpu_carry_hits；carry miss 只能来自 seed/new request/epoch gap。
  • depth2 为 submit q, submit q+1, collect q，且 max_tokens=1 不制造 real q+1。
  • token_d2h_submit_host_ms 是 launch cost；token_d2h_lifetime_ms 可跨 q+1，不应误当 exposed stall。

Overlap 计算

补齐 begin/end timestamp 后，对每个 q 计算：

  • overlap(plan q+1, gpu q)
  • overlap(worker prepare q+1, gpu q)
  • overlap(D2H q, gpu q+1)
  • exposed_host_gap = gpu_start(q+1) - gpu_end(q)
  • overlap_ratio = overlapped_host_work / candidate_host_work

性能统计

  • batch 1/8/32/128 分开；每组 5 次，执行顺序 D1,D2,D2,D1…。
  • 报告 median 与 P95：decode ITL、throughput、schedule、submit、worker prepare、D2H exposed wait。
  • 丢弃 warmup；同一组 request manifest 与 seed 固定。
  • 保留 raw runs，不只保留聚合平均值。

哪些可以隐藏，哪些原则上隐藏不住

工作depth2 目标边界 / 原因
LocalScheduler q+1 plan、snapshot、KV reservation可覆盖在 q GPU 上首个 quantum 没有前驱窗口；若耗时大于 q GPU，尾部仍暴露。
Sequence serialization、DLSlime send、ZMQ command可覆盖RDMA/PCIe/NIC 与 GPU collectives 可能争用，需测净收益。
worker recv/deserialization、prepare_decode、metadata H2D、graph launch host可覆盖只能隐藏 host preparation/launch；q+1 CUDA compute 在同 GPU/stream 上仍排在 q 之后。
q sampled token 作为 q+1 inputGPU carry 消除 host 依赖carry miss 的新 request/epoch gap 必须使用 payload seed，不能猜测 token。
q D2H copy可与 q+1 GPU 部分重叠受 source event、copy engine、带宽与 stream dependency 约束。
q .tolist() / host materialization延迟到 collect，通常可隐藏一部分FIFO commit 前最终仍必须完成；最后一个 flight 没有后继窗口。
q token validation / canonical commit / frontend delta可与已提交的 q+1 GPU 重叠这是计划 q+2 的前置条件，不能无限后移；长尾超过 q+1 GPU 时会暴露。
DP global consensus可放在上一 GPU 窗口仍受最慢 LocalEngine 限制；straggler 超过 GPU 窗口的部分隐藏不住。
首 quantum admission/plan/launch隐藏不住没有可重叠的前一 quantum，直接影响 TTFT。
最后 quantum collect / terminal / release隐藏不住没有后续 useful GPU work；EOS 还可能已有一个必须 drain 的 stale flight。
q 与 q+1 的 GPU compute不并发同 GPU KV 状态与默认执行顺序决定它们串行；本设计目标是隐藏 CPU，不是并行两个 decode compute。
